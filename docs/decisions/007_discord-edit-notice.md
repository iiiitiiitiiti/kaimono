## 007. 送った更新のお知らせは、Actions の手動実行で書き直す

- 日付: 2026-11-25
- 対象: `.github/workflows/discord-edit.yml`・`.github/notify-discord.sh`・`.github/workflows/deploy.yml` の `notify`

006 の更新のお知らせを、あとから書き直せるようにする。足した品物の知らせ（005）は対象外。

### 決定

お知らせを送るときに Discord が返す投稿の番号を、Actions の成果物 `discord-message`（90日残る）に置く。書き直しは手動で動かす流れ `discord-edit.yml` が受け持つ。新しいお知らせの文（1行に1つ）と、書き直す投稿のリンクを渡す。リンクが空なら成果物から最後に送った投稿を探す。送り先のウェブフックの「投稿の編集」で中身を置き換える。見出しと最後の一言は送るときと同じ形で付け直す。

本人が Claude に「最後の投稿を直して」や投稿のリンクを渡したら、Claude が新しい文面を見せて承認を得てから次を動かす。

```
gh workflow run discord-edit.yml -f notes="新しい文" -f message="投稿のリンク（最後の投稿なら空）"
```

### 背景

2026-11-25 に本人がメイン経由で「前に送った投稿をあとから書き換える」機能を頼んだ。ふたりのレシピ帳が先に同じ機能を入れている（送るたびに投稿の番号を残し、ウェブフックの編集で書き換える作り）。かいものの送り先は GitHub のシークレットにあり手元からは読めないので、書き換えも GitHub の中で動かす必要がある。

### 比較した代替案

| 案 | 却下理由 |
|---|---|
| 投稿の番号をリポにコミットして残す | notify ジョブに書き込みの権限が要り、そのコミットがまた公開の流れを動かす |
| 投稿の番号をリポの変数（Actions variables）に残す | Actions が持つ鍵では変数を書き換えられず、別の鍵を本人に作ってもらう手間が要る |
| 書き換えを手元の PC から送る | 送り先の URL が手元に無い。URL を手元に置くと漏れる場所が増える |
| リンクだけで書き直し、番号は残さない | 「最後の投稿を直して」に応えられない。Discord のウェブフックは送った投稿の一覧を返さない |

### 影響範囲

- `notify-discord.sh` はかけいぼ・動物園・水族館ログと同じ中身だったが、かいものだけ書き直しの分が増えた。足した部分は環境変数 `EDIT_NOTES`・`ID_FILE` を渡したときだけ動くので、ほかのリポへそのまま写しても今の動きは変わらない。
- 送るときに `?wait=true` を付け、Discord が返す投稿の中身から番号だけを取り出す。
- 書き直せるのは、このウェブフックが送った投稿だけ（ほかの投稿は Discord が断り、流れが失敗で終わる）。
- 90日より前の投稿は「最後の投稿」として探せない。リンクを渡せば書き直せる。
- 書き直しは頼まれて動かす。そのため次の3つでは失敗で終わらせ、気づけるようにした。送り先の URL が無い。最後の投稿の番号を探せない。新しい文が空である。

### 検証

- 2026-11-25 に手元の bash で `DRY_RUN=1` を使って試した。リンク・番号だけ・末尾の `?` や `/`・読めないリンク・空の文・頭の「お知らせ:」「お知らせ：」「- 」の外し方・記号の逃がし・送り先が無いときの失敗を確かめた。
- 偽の curl に差し替え、新しく送ると `?wait=true` で送って番号をファイルに書くこと、書き直しは `PATCH …/messages/番号` へ送ることを確かめた。
- 成果物の一覧（`actions/artifacts?name=`）が新しい順に返ることを本物のリポで確かめた。
- 本物の Discord での書き直しは、お知らせを1度送るまで試せない（2026-11-25 時点でまだ1件も送っていない）。
